# Demo Mode (SELL ME THIS NOW)

## Purpose

Demo Mode exists to:

- showcase value immediately
- guide the user to a conclusion
- make Cortex feel indispensable

---

## Core Principle

The demo is NOT:

- a feature walkthrough
- a technical showcase

The demo IS:

"A guided realization that current systems are broken and Cortex fixes it."

---

## Demo Narrative (MANDATORY FLOW)

### Step 1 — Bad Input

Start with a weak ticket:

Example:
"SAP not working"

Goal:
Show how bad tickets create friction.

---

### Step 2 — AI Improves Input

User clicks:
"Improve Request"

Show:

- missing details identified
- better structured request
- clear improvement

---

### Step 3 — Reviewer Readiness

Show:

- Ready vs Needs Detail state
- structured clarity
- reduced ambiguity

Goal:
"Can I act on this immediately?"

---

### Step 4 — Routing Decision

Show:

- selected owner
- reasons
- alternatives
- workload awareness

Goal:
"Why THIS person?"

---

### Step 5 — Impact

Show:

- SLA risk reduction
- workload improvement
- ownership clarity

Goal:
"This decision matters"

---

### Step 6 — Rebalance

Show:

- system correcting imbalance
- clear suggestions
- expected impact

Goal:
"The system continuously improves operations"

---

### Step 7 — Metrics

Show:

- reduced follow-ups
- improved readiness
- better routing
- lower SLA risk

Goal:
"This saves time and money"

---

## UI Requirements in Demo Mode

Everything must feel:

- clean
- intentional
- guided

---

### MUST:

- highlight key panels
- reduce noise
- surface important signals first

---

### SHOULD NOT:

- show debug data
- show raw IDs
- overwhelm with options

---

## Highlighted Components

These MUST feel polished:

- Cortex Decision
- Cortex Impact
- AI Triage Panel
- Rebalance Panel
- Workflow Metrics
- Executive Attention Panel

---

## Language Rules (CRITICAL)

Every label should sound like:

"Something a director would say in a meeting"

---

### GOOD:

- "Needs Immediate Attention"
- "Ready for Review"
- "Ownership Risk"
- "Expected Impact"
- "Follow-Up Required"

---

### BAD:

- "AI Output"
- "Computed Result"
- "Data State"
- "Internal Value"

---

## Visual Emphasis

Use emphasis for:

- risk (SLA, blocked)
- decisions
- improvements

---

Do NOT emphasize:

- technical metadata
- internal fields

---

## Interaction Design

Demo must feel:

- fast
- responsive
- controlled

---

### MUST:

- avoid full page reloads
- preserve context (modal, scroll)
- update in place

---

## Rebalance in Demo Mode

Rebalance must:

- feel trustworthy
- show clear cause/effect

Example:

"Move Ticket A from John → Sarah  
→ Reduces SLA risk and balances workload"

---

## AI in Demo Mode

AI must feel:

- helpful
- constrained
- trustworthy

---

### MUST:

- show structured output
- tie to system vocabulary
- feel consistent

---

### MUST NOT:

- feel like magic
- hallucinate values
- override system logic

---

## Metrics in Demo Mode

Metrics must answer:

"Why should I buy this?"

---

### Focus on:

- follow-up reduction
- time saved
- clarity gained
- SLA improvement

---

## Emotional Journey (VERY IMPORTANT)

User should feel:

1. "This looks clean"
2. "Oh… this solves a real problem"
3. "Wait, this explains everything"
4. "This would save us time"
5. "Why don’t we have this?"

---

## Anti-Patterns (DO NOT DO)

- ❌ feature dumping
- ❌ technical explanations during demo
- ❌ inconsistent UI language
- ❌ showing incomplete flows
- ❌ confusing navigation

---

## Demo Data Rules

Demo data must:

- reflect realistic scenarios
- include:
  - bad tickets
  - overloaded users
  - SLA risk cases
  - routing decisions

---

## Golden Rule

Every screen must answer:

"Why does this matter?"

---

## Final Outcome

If demo is successful, the user should say:

"I understand the problem, I see the solution, and I want this."
